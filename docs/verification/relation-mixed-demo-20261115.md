# 종류별 메모 연결 예제 — #168 · 2026-11-15

사용자가 종류별로 연결된 예제를 요청해 기존 텍스트·이미지 외에 터미널·웹의 최소 연결 경로를 구현했다. 앞선 [타입 지원 조사](relation-focus-types-20261115.md)의 미지원 표는 당시 코드 기준이며 이 변경의 상태와 구분한다.

## 구현과 예제 계획

관계 ID를 AppNotes/Terminals/web::Windows의 실제 등록 정보에 따라 `note-ID`·`terminal-ID`·`webview-ID`로 해석한다. 웹은 외부 child가 아니라 등록된 host를 `managed_window`로 찾아 native geometry를 사용한다. 미등록 ID와 overlay 이름은 연결 대상이 되지 않는다. 등록된 노트가 우선하며 ID 문자열의 접두사만으로 유형을 추측하지 않는다.

움직임·resize·숨김·표시 세대 검사와 연결 대상 이벤트 필터도 같은 resolver를 사용한다. 웹의 drag/resize 진입·툴바 숨김·CLI 숨김, 터미널 숨김, 웹 native 닫기에서 관계를 먼저 무효화한다. 기존 메모 하나라도 포커스일 때 전체 선 표시 정책과 150ms 안정화, 겹침 시 숨김을 유지한다. 등록 목록은 관계 파일이 바뀌지 않아도 재조회해 창 재생성에 대응한다.

기존 관계 8개를 보존하면서 전용 순환 예제 4개를 추가하기 위해 개발 프로토타입 상한을 8→16으로 늘렸다. JSON 읽기 상한16KiB·ID/레이블 검증은 그대로다. 프론트엔드는 창별 단일 곡선 payload를 받아 개수 제한이 없으며 공개 API나 영구 관계 저장을 추가하지 않았다.

예제는 ‘기획 텍스트 → 목표 화면 이미지 → 구현 터미널 Welcome → 검토 웹 Welcome → 기획 반영’이다. 이미지 PNG는 검증용 도형이며 실제 화면 캡처로 오인하지 않는다. 셸 명령을 실행하거나 새 외부 사이트를 열지 않는다. 기존 창의 기하·숨김과 원래 관계를 보존하고 새 예제만 추가한다.

### 실제 정렬 함수와의 대조

현재 제품 `placement::stack` 소스를 임시 순수 Rust 프로그램에서 그대로 호출했다. GUI나 앱 프로세스에 접근하지 않는 계산이다. 시작 전 본문 높이·이미지 원본 크기(+툴바22px), 당시 생성 순서와 주 모니터 작업 영역을 사용했다. 새 텍스트 높이는 최초 예제 inspect 값143px를 사용했다. 오른쪽 정렬의 결과를 이후 관측과 비교하니 기존9개와 새 텍스트·이미지2개 **11개 모두 물리 x/y/width/height가 정확히 일치**했다.

예를 들어 기획 메모는[3496,2098,600,206], 기존 캡처는[3496,258,600,378], 새 기획 예제는[3496,50,600,208], 새 이미지 예제는[2896,1900,600,404]였다. 기존 캡처의 너비598→600도 오른쪽 정렬의300 논리px 목표와 정확히 일치한다. 이2px 변화만 OS의 임의 보정으로 설명할 근거는 없으며, 실제 native 반올림의 기여를 별도로 계측한 것은 아니다.

근거는 `/tmp/gibbon168-motion/mixed-demo/right-stack-prediction.json`, `predict-stack.rs`, `before-inspect-session-comparison.json`, `existing-state-comparison.json`, `before.json`, `before-session.json`, `examples.json`, `native.json`, `read-only-followup.json`이다. 임시 진단 자료이며 제품에 테스트 훅을 넣지 않았다.

### 호출 경로와 남은 불확실성

예제 스크립트의 IPC 요청은 list/inspect와 `--serve`뿐이며 새 메모 open이나 전체 정렬 요청은 없다. 관계 파일 로드와 endpoint resolver는 메모 기하의 getter만 사용한다. 위치·크기 setter는 관계선 overlay에만 적용된다. 시작 복원은 saved 기하를 적용하고 화면 경계 접근성을 보정한 뒤 해당 메모를 자동 배치에서 제외한다. 일반 reflow는 이 제외 상태의 창을 장애물로 보존한다.

반면 `layout::arrange(center=false)`는 제외 상태와 관계없이 보이는 텍스트·이미지 메모를 생성 순서대로 오른쪽에 정렬한다. 호출자는 stash의 방향 선택 경로이며 Right 선택과 전체 숨김 복원 뒤 예약된 Right 선택에서 진입할 수 있다. 이 대상 범위와 계산 결과가 관측11개와 일치한다. 전체 숨김의 일반 원위치 복원만으로는 이 오른쪽 stack 결과를 설명하지 못한다.

따라서 **오른쪽 정렬 경로와 동일한 배치가 실행된 정황은 강하지만, 그 입력 주체·경로·정확한 시점은 미확정**이다. 해당 실행에서 entrance trace/local stage 기록을 켜지 않았고 runtime.log에는 방향 입력·정렬 이벤트가 없다. 사용자 동시 조작, 입력 감지 오작동, 예약 동작 중 하나로 단정하지 않는다. 관계선 변경이나 새창 생성이 기존창 자동 정렬을 직접 유발했다는 제품 회귀는 현재 증거로 확인하지 못했다.

새 웹 예제 자체의 최초 inspect와 native 관측 간 이동은 오른쪽 정렬 대상에서 제외되는 웹이므로 위11개 일치와 별개다. 현재 기존9개 원인 조사에서 그 이동의 원인을 확정하지 않았다. 실제 선 표시는 여전히 포커스·곡선 실화면 확인과 구분한다. 추가 재현이 필요하면 입력·정렬·복원 이벤트를 시각과 함께 기록하는 별도 검증 차례가 필요하다. 현재 사용자 배치와 예제4창은 그대로 유지했다.
