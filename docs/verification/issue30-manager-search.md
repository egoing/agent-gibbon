# 관리 창 메모 검색과 반복 조회 검증 (#30)

기준 main `22dc7de7309f8d47772bb0cf1f2c88768f742ef8`, 계획 `3ee80bf59b9b50b0e8547946deeb464729367609`, 작업 브랜치 `codex/issue30-manager-search`. [이슈 #30](https://github.com/egoing/agent-gibbon/issues/30)과 [계획 Draft #211](https://github.com/egoing/agent-gibbon/pull/211).

## 검색과 갱신

- 기존 2초 조회를 유지한다. `manager_notes`의 선택 인자 `knownBodies`가 있으면 같은 ID의 렌더 HTML SHA-256이 일치할 때만 html을 생략한다. 인자 없는 기존 호출과 전체 새로고침은 본문 전체를 받는다. 해시는 본문이 바뀌면 무효화하며 저장 파일에는 넣지 않는다. ID 재사용이나 revision 초기화가 다른 본문 재사용으로 이어지지 않는다.
- 검색은 NFC와 소문자 변환 뒤 문자열을 비교한다. 검색 인덱스는 표시 제목, 원래 제목, 본문 텍스트를 각각 저장한다. 바뀐 본문만 inert HTML template에서 텍스트로 변환하며 요소 속성·스크립트·iframe은 검색하지 않는다. 인라인 강조 사이의 글자는 이어지고 문단·표 셀 경계는 공백이 된다. 실제 상세보기에는 기존 Rust sanitizer가 생성한 HTML을 사용한다.
- 사용자가 직접 선택한 항목이 결과 밖으로 나가면 상세보기를 비운다. 같은 항목이 다시 보이면 복원하고, 새 항목을 직접 고르면 그 선택을 유지한다. 저장소에서 삭제된 선택은 해제한다. 설정에서 목록으로 돌아올 때는 필터를 유지하고 트레이의 더보기는 기존 약속대로 전체 목록을 연다. 목록 검색·선택은 읽기 전용이다.
- 결과를 ID별로 대조하여 필요한 행만 바꾼다. 검색 헤더를 고정하고 결과와 상세를 따로 스크롤한다. 검색 해제 시 전체 목록의 이전 스크롤 위치를 복원한다. 한글 조합 중에는 조합 완료 전의 값을 필터에 반영하지 않는다.
- 마지막 캡처 하나의 데이터 URL을 캐시한다. 다른 메모 갱신은 선택 이미지 DOM과 데이터를 그대로 둔다. 앱의 캡처 파일은 ID별 최초 생성 전용이다. 반복 조회는 revision·파일 크기·수정 시각(macOS는 inode와 상태 변경 시각도 포함)으로 무효화한다. 수동 전체 새로고침은 선택 이미지 파일을 다시 읽어 파일 메타데이터까지 보존한 외부 수정도 반영하며, 같은 바이트면 기존 이미지의 src를 유지한다. 늦게 도착한 이미지 응답과 디코딩 완료는 현재 상세보기와 해당 보기의 최신 요청 번호가 모두 일치할 때만 적용한다. 조회 실패는 기존 데이터와 검색어를 보존하고 다음 조회는 전체 본문으로 복구한다.

## 전송과 DOM 비교

기준과 변경 후 각각 실제 관리 창 HTML/JS/CSS를 독립 Chromium 158에서 실행했다. 네이티브 IPC는 같은 합성 데이터로 대체했다. 1,000개 행 중 첫 항목의 캡처를 선택하고 마지막 항목의 본문과 제목을 바꿨다. 표의 바이트는 요청 인자와 응답을 UTF-8 JSON으로 계수한 합계다. 초기 조회에는 색인 재사용을 위한 토큰과 원래 제목이 추가된다.

| 시점 | 기준 bytes | 변경 후 bytes | 목록과 상세의 관측 결과 |
|---|---:|---:|---|
| 첫 목록 조회 | 6,105,693 | 6,211,571 | 전체 본문 1회 수신, 이후 본문 재사용 |
| 같은 데이터 반복 조회 | 6,105,693 | 259,528 | 변경 후 목록·상세 DOM 변이 0 |
| 타 메모 본문 변경 | 6,105,838 | 265,578 | 목록 1,000개 버튼 교체 → DOM 변이 0, 선택 이미지 요청 1 → 0 |
| 타 메모 제목 변경 | 6,105,846 | 259,544 | 변경 후 해당 버튼의 글자·title만 변경, 선택 이미지 요청 1 → 0 |

변경 후 정기 요청의 77,831 bytes에는 999개 본문 토큰이 포함된다. 간격 콜백을 브라우저에서 직접 실행했고, 실제 DOM MutationObserver와 manager_image 호출 횟수를 기록했다. 수치는 해당 데이터 크기와 조회 형식의 비교다. 네이티브 IPC 직렬화의 프레이밍, OS 메모리, 유휴 CPU와 실화면 시간은 측정하지 않았다. 전역 이벤트 기반 갱신은 별도 [#131](https://github.com/egoing/agent-gibbon/issues/131)의 범위다.

## 큰 캡처의 상세 스크롤 후속 검증

초기 검토 패치에서 높이 1,900px인 캡처를 500px 아래로 읽다가 제목만 변경해도 실제 관리 DOM의 스크롤이 0으로 돌아갔다. 상세 전체를 비운 뒤 비동기로 이미지를 붙이는 사이 브라우저가 짧아진 콘텐츠 높이에 맞춰 위치를 제한했다.

같은 ID의 캡처는 도구와 제목 노드를 유지하고, 이미지가 바뀌면 새 픽셀의 디코딩이 끝날 때까지 이전 이미지를 유지한다. 오래된 스크롤 값을 나중에 다시 쓰지 않는다. 브라우저에서 제목 갱신 후 500px 유지, 이미지 응답 대기 중 670px로 이동, 디코딩 완료를 보류한 동안 720px로 다시 이동, 높이 1,800px 이미지 교체 후 720px 유지를 확인했다. 새 이미지가 더 짧아 기존 위치를 표시할 수 없을 때의 최대 스크롤 범위는 브라우저가 정한다. 같은 ID에서 먼저 시작한 응답이 뒤늦게 와도 최신 이미지가 유지되는 회귀 검사도 통과했다.
