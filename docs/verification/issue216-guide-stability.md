# #216 세 보조키 방향 안내 깜박임

수정 전 WebKit에서는 안내가 이미 펼쳐져 있어도 열기를 호출할 때마다 새 SVG를 요청하고 아이콘이 사라진 프레임을 그렸다. 네이티브 코드도 새 조합의 첫 보조키에서 열린 창을 즉시 숨겼다. 후자는 코드에서 확인했으며 물리 키 입력으로 재현하지 못했다.

## WebKit 화면 비교

macOS에서 같은 232pt WKWebView에 기준 커밋과 작업본의 방향 안내 HTML을 차례로 로드했다. 테스트 창은 포커스를 받지 않고 마우스 입력을 통과시켰다. 로컬 WKURLSchemeHandler가 각 버전의 파일을 같은 tauri://localhost 주소로 제공했다. 각 호출 직후 WKWebView.takeSnapshot을 요청하고, 250ms 뒤 다시 캡처했다. 직후 캡처는 도구가 얻은 첫 표본이며 모니터의 모든 프레임을 측정한 것은 아니다.

| 464×464 캡처에서 RGB 세 성분이 모두 70 미만인 픽셀 수 | 첫 숨기기 | 숨기기 반복 | 복원 전환 | 복원 반복 | 숨기기 전환 |
|---|---:|---:|---:|---:|---:|
| 수정 전 호출 직후 | 0 | 0 | 0 | 0 | 0 |
| 수정 후 호출 직후 | 0 | 12731 | 14649 | 14649 | 12731 |
| 250ms 뒤, 수정 전후 동일 | 12731 | 12731 | 14649 | 14649 | 12731 |

초기 페이지 로드 이후 수정 전에는 열기 다섯 번에 SVG를 다섯 번 요청했고, 수정 후 추가 요청은 0회였다. 수정 후 첫 열기에는 펼침 애니메이션 4개가 시작됐고 이어진 네 번에는 재시작하지 않았다. 다섯 최종 프레임은 수정 전후 RGB 픽셀이 각각 일치했다. 닫기 후 캡처의 어두운 픽셀은 0개였고 복원용 안내를 다시 열었을 때 14649개였다. Chrome에서 동작 줄이기를 에뮬레이션했을 때 첫 열기 애니메이션은 0개였으며 두 눈 아이콘의 상태 구분과 즉시 닫기를 확인했다.
