## 표시 순서

기준 코드에서는 영역 선택이 끝나면 마스크를 정리하고 새 창의 크기·위치를 지정한 뒤 바로 창을 표시했다. 네이티브 창은 처음에는 숨김 상태이고, 웹 문서는 별도로 시작한다. 텍스트 편집기 초기화, 캡처 이미지 조회·디코딩, 메모별 색 조회와 CSS 적용은 창 표시 조건에 포함되지 않았다. 방향 안내 아이콘은 별도 창이다.

이번 변경에서는 드래그로 만든 창만 실제 창 레이블로 등록한다. 배치 완료 후 로컬 문서가 메모 정보를 읽고, 편집기·이미지·시작 화면과 테마를 반영한 뒤 레이아웃을 확정하고 표시를 요청한다. 이미지 준비는 실제 디코딩을 기다린다. 원격 웹 문서에 스크립트나 권한을 추가하지 않는다. 기존 창을 다시 열 때는 최초 표시 요청을 만들지 않으며 개별 숨김이나 파기 뒤 늦게 도착한 요청은 창을 다시 열 수 없다.

## macOS 실측 방법

같은 워크트리에서 기준 커밋과 수정본을 각각 빌드했다. 개발 CLI로 표식 메모의 본문과 응답 인스턴스를 확인하고 실행 파일 경로, PID, 네이티브 창 제목과 창 번호를 대조했다. 디자인 변경 시험은 수정본과 SHA-256이 같은 실행 파일을 별도 이름으로 복사하여 독립 WebKit 저장소에서 실행했다. 설정창에서 디자인을 선택한 뒤 자기 PID의 트레이 메뉴와 선택 마스크를 확인하고 같은 좌표를 드래그했다.

세 화면이 연결된 환경의 2배율 화면에서 (260, 225)~(600, 450) pt를 선택했다. 텍스트·터미널·웹 창의 기대 영역은 (260, 225, 340, 225) pt이고, 이미지 창은 상단 도구 영역을 포함해 (260, 203, 340, 247) pt다. ScreenCaptureKit 스트림은 드래그 전에 시작했다. 대상 PID의 새 창만 포함하고 기존 창과 포인터를 제외했다. (310, 310)에서 96×64 pt(192×128 px)를 120 fps로 요청해 전송된 완성 프레임을 기록했다. 시간은 첫 비투명 샘플 기준이며 디스플레이 전체나 모든 주사 시점에 대한 측정은 아니다.

기준 커밋의 기본 회색 웹 창에서는 먼저 흰색 단색이 세 번 기록됐고 약 233 ms 뒤에 시작 화면이 보였다. 이미지는 밝은 바탕 뒤 약 33 ms에 캡처 픽셀이 보였다. 중간 수정본에서는 웹·텍스트 창 크기를 지정하면서 macOS가 상단 위치를 옮기는 현상과 컬러 터미널의 첫 샘플에서 회색이 약 33 ms 남는 현상을 확인했다. 텍스트·웹은 최종 크기 지정 후 위치를 맞추고, macOS에서는 숨겨진 로컬 WebView의 화면 갱신을 기다리는 1 pt 스냅샷의 완료 콜백에서 창을 표시한다. 채취한 이미지는 즉시 폐기한다. WebKit이 오류를 반환하면 준비된 로컬 화면을 열어 사용자가 계속 조작할 수 있게 한다. [Apple WKSnapshotConfiguration](https://developer.apple.com/documentation/webkit/wksnapshotconfiguration/afterscreenupdates)

갱신 완료만 기다린 중간 빌드에서도 검정 텍스트에 이전 회색이 약 33 ms 기록됐다. 최종 빌드는 영역에서 생성한 텍스트·이미지·터미널 문서만 파싱 시작 시 투명하게 두고, 테마·내용 준비 후 같은 작업에서 불투명 상태를 복구한다. 일반 메모 생성·복원은 기존 표시 경로를 사용한다.

콜백은 등록 당시의 세대 토큰을 보관한다. Rust 검사에서 배치 완료 후 숨김·파기를 나타내는 취소를 수행하고 같은 레이블에 새 창을 배치한 뒤 이전 세대 콜백을 호출했다. 이전 콜백은 표시 권한을 받지 못했고 새 세대 콜백만 정확히 한 번 권한을 받았다. 이 순서는 결정적인 상태 테스트로 검증했다.

## 최종 실측 결과

수정본 SHA-256은 `2257ed87c1b070e5fbbed047de638b58a0b1ab7f87a828c2f81e0df2c4c34952`이다. 흰색·검정·컬러·기본 회색에서 각각 네 종류를 새로 만들어 기준 커밋 16건과 수정본 16건을 비교했다. 수정본 16건 전부 첫 비투명 샘플을 읽은 시점의 창 번호와 사각형이 선택한 위치·크기와 일치했다. 같은 창을 숨겼다가 열어 창 번호와 메모 데이터를 다시 확인했다.

| 디자인 | 텍스트 첫 배경 RGB | 터미널 첫 배경 RGB | 이미지 첫 샘플의 서로 다른 RGBA 수 | 웹 첫 샘플의 서로 다른 RGBA 수 |
|---|---|---|---:|---:|
| 흰색 | 248, 248, 248 | 248, 248, 248 | 163 | 90 |
| 검정 | 38, 38, 39 | 38, 38, 39 | 300 | 106 |
| 컬러 | 77, 77, 75 | 189, 214, 87 | 503 | 115 |
| 기본 회색 | 222, 226, 221 | 222, 226, 221 | 226 | 108 |

흰색 디자인에서도 웹 시작 화면의 이동 버튼 경계와 글자가 첫 샘플에 포함됐다. 컬러 디자인에서는 메모마다 배정한 색이 다르므로 각 창의 초기값을 같은 창의 안정된 프레임과 비교했다. 이미지는 첫 샘플에서 캡처 내용이 보였다. 촬영 중 포인터가 창에서 벗어났을 때 적용되는 기존 반투명 효과는 배경색 판정에서 구분했다.

기본 회색의 정규 개발 실행 파일 PID 20664에서 웹은 로컬 페이지 주소와 요청 횟수(1회), 터미널은 실행 중인 셸 PID 21760, 텍스트는 입력·저장한 본문, 이미지는 캡처 정보를 숨김·다시 열기 뒤 유지했다. 촬영마다 실행한 자기 앱과 테스트 창을 정리했고 이전 전면 앱으로 포커스가 돌아왔음을 확인했다. macOS Intel과 Windows의 네이티브 첫 프레임은 실측하지 않았다.

## 선행 변경과 통합 검사

38번 최종 패치 `a76ae3b6`와 39번 after-native 코드 `1a5b38c4`·문서 `8de56d8d`를 적용했다. 38번 툴바 치수·웹 콘텐츠 경계, 39번 선택 마스크의 Esc 입력, 40번 마스크 정리 후 새 창의 첫 표시는 서로 다른 단계다. 각 패치의 변경 구간이 보존됨을 역방향 적용 검사로 확인했다. 39번 초단 Esc 실검증의 한계는 [해당 기록](issue219-selection-escape.md)에 남아 있다.

통합 트리에서 Rust 305개 통과·1개 기존 제외, UI 221개 통과. UI 검사에는 숨은 복원 창과 약관 확인 전 IPC가 거절된 창이 이후 정상 초기화되면서 자동 표시되지 않는 두 경우와 Welcome 준비가 실패해도 테마 준비를 기다린 뒤 오류를 표시하는 경우를 포함한다. 배치 전 잘못된 준비 응답, 배치·문서 준비의 두 순서, 창별 단 한 번의 표시, 숨김·파기 뒤 지연 응답 억제를 Rust 검사에 추가했다. Rustfmt·Clippy·macOS 개발 빌드를 통과했다.

헤드리스 검사는 실제 HTML/CSS·편집기·xterm을 여는 `node scripts/region-first-frame-smoke.mjs`로 실행했다. Chrome 360×240 CSS px, DPR 2에서 메모 네 종류와 흰색·검정·컬러 디자인을 조합했다. IPC 배치 응답과 내용 응답을 보류하고, 표시 요청 수·CSS 토큰·내용·레이아웃을 확인했다.

헤드리스 추가 2건에서는 이미지 조회와 터미널 Welcome의 최초 응답을 각각 거절했다. 두 화면 모두 검정 테마의 기존 상태 영역에서 오류를 읽을 수 있었고 첫 표시 요청은 한 번이었다. 이미지 재조회 성공 후 동일한 창에 실제 이미지가 로드됐다. 정상 12건과 합쳐 14건이다.
