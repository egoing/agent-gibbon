# 첫 메모·터미널 실행의 관리창 노출 방지

2026-11-21, 병합·배포 전의 전용 워크트리 변경이다.

## 원인과 수정

Wry 0.57.0은 WKWebView를 붙일 때 NSApplication의 활성화를 요청하고, Tao 0.37.1도 시작 시 활성화를 요청한다. macOS가 이 요청의 알림을 늦게 전달하면 기존의 한 번짜리 메인 큐 억제가 끝난 뒤 앱 선택으로 오인했다. 빈 저장소에서 첫 메모를 열 때 관리창이 나타나는 실행과, 세션 복원 후 전경 앱이 바뀌는 실행을 추적했다. 트레이 영역 텍스트 선택 뒤 편집기의 의도적인 포커스 요청도 같은 자동 관리창 처리로 들어갔다. 터미널에는 비활성 표시 뒤 일반 show()를 중복 호출하는 경로도 있었다.

일반 창 생성과 앱 준비 구간에서는 AppKit의 공개 activate/activateIgnoringOtherApps: 요청을 원천 억제한다. 메서드 래퍼는 프로세스에 한 번 설치하지만 억제는 중첩 가능한 메인 스레드 RAII 구간에만 적용하며, 밖에서는 기존 구현으로 그대로 위임한다. macOS 14 이전의 legacy 메서드와 이후의 activate 메서드를 모두 처리한다. 임의 시간 지연은 추가하지 않는다.

영역 선택 오버레이·새 텍스트 편집기의 의도적인 포커스는 유지하고, 해당 요청으로 생긴 활성화 알림만 자동 관리창 처리에서 제외한다. 실패한 요청은 표식을 해제한다. 명시적 관리창 열기는 이 상태를 해제하고 대기 중인 일반 창 포커스 복원도 폐기한다.

설치 앱의 CLI 자동 시작에는 `open -g … --args --serve`를 사용한다. 인자 없는 macOS 앱 실행과 Dock Reopen은 관리창을 여는 명시적 경로다. 필수 약관 안내와 직접 앱 실행의 관리는 앱 준비가 끝난 Ready 이후에 열어 시작 억제 구간과 분리한다. 로그인 자동 실행·다른 플랫폼의 기존 정책은 유지한다.

## 검증 범위와 남은 한계

Conf 5는 위 macOS ARM64 개발 앱에서 실제 확인한 경로에 한정한다. Risk Medium: 프로세스 내부 AppKit 활성화·포커스 상태에 영향을 준다. Windows, Intel Mac, macOS 14 이전 실기기, 서명된 설치 앱·업데이트 설치·전체 플랫폼 릴리스 빌드는 실행하지 않았다. 설치 앱의 LaunchServices 자동 시작 인자 변경은 코드 검토 범위이며 실제 설치본은 교체하지 않았다. 업데이트 스냅샷 복원은 같은 시작 억제 구간을 사용하지만 실제 업데이트 설치 후 재시작은 별도 검증 대상이다.

AppKit에는 ⌘Tab 전용 활성화 출처가 없으므로 생성 구간 밖에서 외부 프로그램이 앱을 활성화하는 경우를 모두 구별한다는 보장은 추가하지 않는다. 실제 키 입력 시험은 현재 실행 중인 앱의 MRU 순서에 영향을 받으므로 PID와 최종 전경을 함께 확인했다. Dock 검사는 실제 Dock 클릭 대신 동일한 Reopen 이벤트를 해당 개발 PID로 직접 전송했다.

커밋·push·병합·배포·설치 앱 교체는 수행하지 않았다.
